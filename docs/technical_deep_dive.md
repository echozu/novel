## 一、项目背景：为什么市面上的 AI 拆书是玩具

目前主流的"AI 拆书"产品有一个共同问题：它们把整本书送进大模型，要求输出摘要。这个思路在短文本上可行，但面对百万字以上的长篇网文就失效了，原因有以下几点。

**第一，上下文窗口不够。** 一部标准网文平均 200 万字，折合约 100 万 token。即使最大的 Claude 200K 窗口也只能放进约五分之一。超出的内容模型根本"看不到"。

**第二，即便塞进去，注意力也不均匀。** 大模型在超长输入时存在"中间丢失"现象——开头和结尾会被正常处理，中间大段内容实际上被模型降权。一部 3000 章的小说，有 2500 章的细节是失效的。

**第三，输出是摘要，不是结构。** 一次性摘要只能告诉你"主角历经磨难最终成功"，但没有办法告诉你：哪几章节奏最慢、第 150 章的反转和第 800 章的回收之间是什么关系、情感线在全书跨度上有没有完整的起承转合。

**第四，没有可复用资产。** 摘要是给人读的，不是给下游 AI 创作用的。你无法把摘要直接交给 Claude 说"你帮我写同款小说"。

novel-lab 解决的核心问题是：**如何让大模型对一部超长小说做出有深度、有证据、可复用的结构化分析。**

## 二、核心设计思想：分层金字塔 + Map-Reduce

novel-lab 的整体架构来源于一个直觉：**不同粒度的问题要在不同粒度上回答。**

章节级的问题（"这一章有什么爽点？主角说了什么金句？"）只需要看这一章。全书级的问题（"主线是什么？人物弧光如何？"）只需要看章节级的摘要汇总，而不需要再读原文。深度洞察的问题（"为什么读者愿意追读？这本书的差异化在哪？"）只需要看全书结构，同样不需要读原文。

这就形成了一个自然的金字塔：

```
原文（百万字）
    ↓
章节级证据（每章 500-800 字的结构化 JSON）
    ↓
全书级结构（情节线、人物、节奏、文风）
    ↓
深度洞察（差异化、爽点公式、弃书风险）
    ↓
创作资产（报告、创作宪法、写作包）
```

越往下，信息量越小但意义越大，每一层只处理上一层的输出，不回溯原文（除非 RAG 需要）。这就是整个系统的核心设计逻辑。

## 三、Layer0：文本预处理

### 3.1 文件解析

系统支持 TXT 和 EPUB 两种格式。

对于 TXT，中文网文的编码历史比较复杂，很多老文件是 GBK 或 GB18030 编码。系统会按顺序尝试 utf-8、utf-8-sig、gbk、gb18030、big5 几种编码，取第一个成功解码的结果。如果都失败，则用 utf-8 忽略错误字符强制解码，保证流程不中断。

对于 EPUB，系统用 ebooklib 读取 EPUB 包，提取所有 HTML 文档，用 BeautifulSoup 把 HTML 转成纯文本，再把多个文档拼接成一个完整文本，然后走和 TXT 相同的章节切分逻辑。

### 3.2 章节切分

章节切分是整个流程的起点，切得对与不对直接影响后续所有分析质量。

切分逻辑基于中文章节正则表达式。支持的格式包括：`第N章`、`第N回`、`第N节`、`第N折`，其中 N 既支持阿拉伯数字也支持中文数字（零一二三四五六七八九十百千万两）。同时支持识别卷信息，如`第一卷`这类标记，方便后续做卷级汇总。

正则识别到章节边界后，每个章节的标题和正文会被分别提取，生成一个标准化的章节对象，包含章节序号、标题、正文、字数统计，以及所属卷（如果有的话）。

如果文件里根本没有任何章节标识符（比如一些短篇或者格式特殊的文本），整本文件会被作为一章处理，保证流程不崩溃。

整本书的元信息（书名、book_id、章节数、总字数）会在这一步生成。book_id 是基于书名和正文前 5000 字的 SHA1 哈希值，保证同一本书多次处理得到相同 ID，便于断点续跑复用缓存。

### 3.3 语义切块

章节切分是"粗粒度"的，一章通常有 2000-5000 字，直接拿去做向量检索粒度太粗。所以需要进一步把每章切成更小的语义块。

切块使用 LangChain 的 RecursiveCharacterTextSplitter，分隔符优先级从高到低：双换行（段落分隔）、单换行、句号、感叹号、问号、分号、逗号、空格。这样切出来的块优先在段落和句子边界分割，保留语义完整性。

默认 chunk size 约 384 token，overlap 约 64 token（前后两个块之间有重叠，避免跨块的语义被截断）。token 数估算用 tiktoken 的 cl100k_base 词表，离线环境下按中文字符数 × 0.6 兜底。

每个 child chunk 记录所属章节序号，这样向量检索命中之后就能追溯回哪一章。

### 3.4 向量索引与 RAG

向量索引使用 Chroma 作为持久化存储。Chroma 是一个轻量的本地向量数据库，不需要额外起服务，直接以文件夹形式存储在工作目录里。

向量化使用阿里云百炼的 text-embedding-v4 模型，通过 OpenAI-compatible 接口调用。这个模型支持 1024 维向量，对中文语义理解效果比大多数本地小模型好，API 调用成本也相对较低。

text-embedding-v4 有一个限制：每次请求最多 10 条文本输入。系统会自动把 batch size 控制在 10 以内，避免超限报 400 错误。

索引建好之后支持两种检索用途：

- **Critic 校验时**，根据 evidence_chapter 字段直接取对应章节原文，不走向量检索，是精确匹配。
- **情节线复核时**，用语义查询（如"后半段关键转折 伏笔回收 终局"）检索最相关的章节片段，把原文证据返回给 LLM 参考。

向量索引支持断点复用：如果 Chroma 里已有这本书的向量，默认直接加载，不重新 embedding。只有设置了强制重建标志才会重新计算。

## 四、LLM 路由层：多模型统一管理

整个系统会在不同阶段用到不同模型。路由层的设计目标是：**用最少的成本，在最关键的地方用最好的模型。**

### 4.1 角色路由

系统把 LLM 任务分成四种角色：

- `map`：章节级分析，量大但单任务简单
- `reduce`：全书聚合，量小但任务复杂
- `critic`：证据校验，需要严格逻辑
- `deep`：深度洞察与创作宪法，需要高质量输出

然后通过"档位（tier）"来决定每种角色用哪个模型：

| 档位 | map | reduce | critic | deep |
|---|---|---|---|---|
| basic | DeepSeek | DeepSeek | DeepSeek | DeepSeek |
| balanced | DeepSeek | Claude | Claude | Claude |
| premium | Claude | Claude | Claude | Claude |
| local | 本地模型 | 本地模型 | 本地模型 | Claude |

这样设计的考量是：Map 阶段每章都要调用一次 LLM，量大，用 DeepSeek（约 $0.14/1M token）比 Claude（约 $3/1M token）省 20 倍成本，而单章任务难度适中，DeepSeek 完全胜任。Reduce 和洞察任务量小，但质量影响最终报告，值得用更好的模型。

### 4.2 工程保障

路由层不只是模型选择，还封装了以下工程能力：

**限流**：使用 aiolimiter 按后端分别限流（DeepSeek 60 RPM、Claude 50 RPM）。如果超过限制，调用会自动等待，不会报错崩溃。

**重试**：使用 tenacity 做指数退避重试，最多重试 5 次，等待时间随重试次数指数增长，最大等待 30 秒。网络抖动、临时限速等问题都能自动恢复。

**缓存**：所有 LLM 响应基于请求内容（messages + model + system prompt）做哈希，结果写入 SQLite。同样的请求只调用一次 LLM，断点续跑不重复花钱。

**成本统计**：每次调用后根据 token 数和当前模型价格计算费用，累计到全局计费。最终会在报告和控制台汇总显示。

**Key 预检查**：如果使用 balanced 或 premium 档位，但 ANTHROPIC_API_KEY 仍是占位值（如 `sk-ant-xxxxxxxx`），系统在启动时就会输出红色警告并告知影响，而不是等到任务执行到一半才崩溃。

## 五、Layer1：章节级 Map Agent（系统质量的基础）

Map 阶段是整个系统质量的决定性环节。输入是原始章节文本，输出是结构化的章节分析 JSON。

### 5.1 为什么要"一章一次调用"

直觉上，把多章合并送给 LLM 可以减少调用次数。但这有几个问题：

- 多章合并后上下文变长，模型容易在章节边界混淆
- 一章失败会连累整批结果
- 无法做章节级断点续跑

更重要的是，每章独立处理可以**完全并发**。一部 3000 章的小说，20 个并发任务同时跑，整个 Map 阶段只需要约 150 次串行时间，而不是 3000 次。

### 5.2 单次 Map 输出什么

每章分析输出的内容，可以理解为"读书笔记"，但比普通笔记更结构化：

**摘要**：80-150 字，要求包含主要事件和状态变化，不能只写"主角继续冒险"这种无信息量的句子。

**人物提及**：这一章出现了哪些人，他们做了什么，情绪状态如何，和其他人物的关系有没有变化。这是后续人物弧光分析的数据来源。

**场景**：地点、时间线索、参与者。这是后续知识图谱里 Location 节点和 SET_IN 关系的来源。

**钩子与爽点**：这是整个系统最重要的数据之一。每个钩子记录类型（章末悬念、打脸反转、升级突破等共 10 种）、强度（1-5 分）、在章节中的位置（开头/中段/末尾）、以及直接从原文复制的片段证据。强度 5 代表读者绝对不会弃书的大爽点，强度 1 代表轻微钩子。

**金句**：要求必须从原文原句提取，不能改写。系统会用字符串包含检查来验证金句确实在章节文本里，如果不在就过滤掉。这避免了 LLM 编造或意译金句。

**套路命中**：题材相关的常见套路，比如玄幻里的"打脸打脸再打脸"、"升级流"等。套路来自预设的题材套路库，LLM 只能选库里有的 ID，不能自己发明新套路。

**线路信号（line_signals）**：这是近期新增的关键字段，专门为解决"主线/暗线断裂"问题而设计。

### 5.3 线路信号：提前在第一层打标

主线/暗线断裂的根本原因是：Reduce 阶段的模型只有摘要和钩子作为输入，面对一部 3000 章的小说，它很难仅凭摘要就判断"哪一章推进了经济暗线"。

解决办法是：**在第一层就让模型给每章标注"这章推进了哪条线"**。

线路信号的结构是：

- `line`：属于哪条线（main/economic/power/emotional/sub/none）
- `status`：这章在这条线上处于什么阶段（setup=铺垫、advance=推进、twist=转折、payoff=兑现、cooldown=收束）
- `event`：发生了什么动作（要求填具体行为，不能只写"情感推进"）
- `impact`：造成了什么影响（要求填具体变化，和 event 形成因果对）
- `characters`：涉及哪些角色
- `snippet`：原文证据片段

有了这个字段之后，Reduce 阶段在聚合情节线时就有了每章级别的锚点，不再是盲猜。

### 5.4 并发调度与断点续跑

Map 阶段使用 asyncio 协程实现并发，通过 Semaphore 控制最大同时运行的任务数（默认 20）。

每章分析有超时保护：默认 420 秒（可配置）。如果单章超时，该章会被标记为失败，系统继续处理其他章节。这避免因为某一章网络问题或 LLM 响应慢而卡死整个流程。

每章分析完成后，结果立刻写入 SQLite。如果流程中断，重启后已完成的章节直接从数据库读取，不重新调用 LLM。这是最省钱的设计之一。

## 六、Layer2：Reduce 聚合——把章节证据汇聚成全书结构

当所有章节的 Map 分析完成后，我们手里有的是一堆结构化的"读书笔记"，而不是全书的理解。Layer2 的任务是把这些分散的章节级证据汇聚成全书级的结构性认知。

### 6.1 节奏分析（确定性计算，不依赖 LLM）

节奏分析是 Layer2 里唯一不依赖 LLM 的模块，完全用确定性算法计算。

做法是：遍历所有章节的钩子，提取每章的最大爽点强度，画出一条完整的强度曲线。这条曲线就是"爽点密度分布图"。

然后在这条曲线上计算：
- **平均高峰间隔**：找出所有 intensity ≥ 4 的章节，计算相邻两个高峰之间的间隔平均值。网文 top10% 爆款的基准是每 1.8 章一个高峰，间隔越短说明节奏越紧凑。
- **每章小钩子数量**：所有 intensity ≥ 1 的钩子总数 ÷ 章节数。
- **弃书风险区间**：连续若干章（默认 3 章）maxIntensity ≤ 2，这段区间就被标记为弃书风险。读者在这里最容易流失。
- **大高潮章节**：intensity = 5 的章节列表，这些是全书最重要的节点。

这个模块之所以做成确定性计算而不用 LLM，是因为：节奏分析的结果需要稳定可复现，而且计算逻辑很明确，不需要语言理解能力。

### 6.2 人物弧光追踪

人物弧光模块的输入是所有章节的人物提及记录，目标是生成每个主要人物的完整传记和状态变化轨迹。

首先做一步"别名归并"：同一个人物在不同章节可能被称为不同的名字（比如"孙悟空"和"猴哥"）。系统用简单的名字包含关系做启发式归并——如果两个名字互相包含对方，就认为是同一人物。这虽然不完美，但对大多数中文小说场景够用。

归并之后，按出现频率排序，取出现最多的 12 个人物（默认值）重点分析。这样可以控制 LLM 调用次数，避免把边缘路人角色也做完整分析。

然后分批（每批 4 个）把人物的出场记录送给 LLM，要求输出：
- 人物的核心角色定位（主角/反派/配角/导师/CP 对象）
- 动机：这个人物的根本驱动力是什么
- 缺陷：这个人物的弱点和局限性
- 五状态弧光：initial（起始状态）→ catalyst（触发事件）→ turn_25（25% 处状态）→ turn_50（中段转折）→ turn_75（后半段）→ final（最终状态），每个状态点附章节号、状态描述和心理变化说明
- 关系演化：与其他主要角色的关系类型及变化过程

弧光的五状态点设计来源于网文写作方法论"666 方法论"——一个好的人物弧光在 25%、50%、75%、100% 处都有明显的状态变化，而不是从头到尾没有成长。

### 6.3 主线/暗线分离

这是 Layer2 最复杂的模块，也是整个系统里设计迭代最多的部分。

**基本逻辑**：把所有章节的摘要、钩子、line_signals 打包，让 LLM 归纳出：
- 一条主线（main）：贯穿全书的核心冲突与目标
- 经济暗线（economic）：财富、资源、利益分配的争夺与流动
- 权力暗线（power）：势力博弈、信息差、上下级关系
- 情感暗线（emotional）：爱情、亲情、友情的发展与变化
- 副线（sub）：配角线、单元故事等

**分批策略**：对于超过 80 章的小说，系统不会一次性把所有章节摘要送给 LLM（那样 prompt 会非常长）。而是按每 50 章一批，先生成局部情节线，再用 LLM 把所有局部情节线合并成全书情节线。这个"分批 + 合并"的策略是 Map-Reduce 模式在子模块内部的体现。

**每条线输出什么**：每条线有名称、整体描述摘要、按章节升序排列的关键事件列表，以及与主线的交汇点。交汇点很重要——它是暗线和主线发生交叉推进的章节，通常也是节奏高潮所在。

### 6.4 情节线连续性修复（Layer2.5）

即使有了 line_signals，LLM 输出的情节线还是可能出现断裂：某条暗线有前 30 章的事件，然后中间跳跃到后 200 章，中间 170 章的推进完全消失。这就是"没头没尾"的问题。

连续性修复分两个层次进行：

**第一层：LLM 复核（RAG 辅助）**

系统构造一个新的 LLM 调用，输入包含：初版情节线、章节流水（含 line_signals）、关键章节索引、以及 RAG 检索回来的中后段关键章节片段。

RAG 检索使用的 query 包括"后半段关键转折 伏笔回收 终局"、"人物关系逆转 阵营变化"等，专门针对容易被遗漏的中后段内容。这样 LLM 在复核时有实际的原文依据，能看到中后段确实发生了什么，从而补完断裂的情节线。

给 LLM 的要求非常明确：主线必须覆盖前 25% 和后 25% 的章节区间；每条线若前后事件间隔超过阈值，必须补"承接事件"；末段必须有"阶段回收"。

**第二层：确定性修复**

LLM 复核之后，系统还会对结果做确定性的修复扫描：
- 同一章节出现多个事件时，只保留置信度最高的那个
- 相邻事件章节间隔超过阈值（根据书的总章数动态计算）时，在中间章节插入一个"承接推进"节点
- 最后一个事件章节位于全书前 75% 之前时，在最后一章插入一条"阶段回收"锚点
- 主线的第一个事件章节超过全书前 25% 时，在第一章插入一条"主线起势"

这些确定性修复保证了即使 LLM 输出不完美，情节线依然不会在时间轴上出现明显断裂。

**最终指标 line_continuity**

修复完成后系统会计算每条线的连续性指标：
- 事件数量
- 覆盖区间（从第几章到第几章）
- span_ratio（覆盖章节范围占全书比例）
- tail_covered（是否覆盖全书后 25%）

这些指标会在报告首页展示，让用户直观看到哪些线"贯穿全文"，哪些线"头重脚轻"。

### 6.5 文风指纹分析

文风分析的核心挑战是：不能把全书喂给模型（太长），但也不能只看开头几章（可能风格不稳定或者有早期写作质量差的问题）。

解决方法是**均匀抽样**：从书的开头、中段、末尾分别抽取若干段落，每段截取 800 字左右，共 10 段。这样既控制了 token 数，又保证样本覆盖全书不同阶段的文风。

让 LLM 分析这 10 段样本，输出：
- POV（叙事视角）：第一人称/第三人称限知/第三人称全知
- 时态：过去时/现在时
- 平均句长
- 对白占比
- 描写浓度：浓墨重彩/极简白描/适中
- 修辞手法列表
- 调性关键词
- 标志性句式（3-5 条，这是文风复刻最重要的素材）
- 示例段落（用于 AI 写作包的 few-shot）

## 七、Layer3：深度洞察——把结构翻译成判断

Layer2 产出的是"这本书的结构是什么"，而 Layer3 要回答的是"这本书为什么能/不能留住读者"。

### 7.1 全书上下文压缩

在进行 Layer3 分析之前，系统需要把 Layer2 的大量结果压缩成一个更紧凑的全书上下文，才能在一次 LLM 调用中放得下。

压缩策略：
- top 30 个最强钩子（按 intensity 排序），每个包含章节号、类型、强度、描述和原文片段
- 情节线简化版（不展开每个事件，只保留线名、描述、事件数量和前 6 个关键事件）
- 前 8 个主要人物的简化档案
- 节奏数据（平均高峰间隔、弃书风险区间等）
- 文风摘要
- 所有章节摘要的 80 字截断版
- 题材套路库和反模式（什么样的写法在这个题材里是禁忌）

这个压缩后的上下文通常在 10-20K token 之间，适合作为 Layer3 的输入。

### 7.2 三类洞察

**差异化分析**：这本书相比同题材普通作品，有哪些独特之处让它能脱颖而出？

LLM 要输出若干差异点，每条包含：维度（设定/人设/节奏/文风/价值观/题材融合）、具体描述、为什么这个差异化有效（从读者心理角度解释）。每条都需要附 evidence_chapter，说明这个差异点体现在哪几章。

**读者爽点归因**：读者追读的心理动机是什么？

这不只是说"这本书有很多打脸"，而是要说清楚打脸这个模式触发了读者的哪种心理机制——公平感（坏人受到惩罚）、替代体验（读者通过主角实现了现实中做不到的事）、智识满足（谜题被解开）、情感张力（CP关系推进）等。

每条爽点公式要附典型章节列表，说明哪些章节是这个模式的最佳实例。

**弃书风险识别**：哪些地方的读者最可能流失，为什么，如何修复？

每条风险记录章节区间、原因说明和修复建议。修复建议要足够具体，比如"在 ch200-ch230 区段安排一次阶段性收益（升级/反转/关系突破任选其一）"，而不是"节奏需要更紧凑"这种废话。

### 7.3 Critic：基于原文的结论校验

这是系统防止 LLM 幻觉的最后一道防线。

**问题背景**：LLM 可能会输出听起来合理但实际上没有原文支撑的结论，比如说"这本书的核心差异化在于主角的道德两难困境"，但原文里主角根本没有明显的道德挣扎。

**Critic 的做法**：

1. 收集 Layer3 输出的所有结论（差异点、弃书风险、爽点公式）
2. 每个结论都有 evidence_chapter 字段，根据这个字段取对应章节的原文文本
3. 把"结论 + 原文证据"一起送给 Critic LLM，让它判断：这个结论是否有原文支撑？如果没有，问题在哪？
4. Critic 通过的结论保持原 confidence，没通过的降低 confidence 为 0.3 以下

**关键设计**：Critic 不直接删除失败的结论，而是降低置信度。这样做的原因是：如果粗暴删除，最终报告可能出现某个分析模块为空的情况，影响报告整体质量。保留但标注低置信度，让用户自己判断是否采用，比强制删除更合适。

## 八、Finalize：质量门与确定性兜底

所有 LLM 驱动的模块都有可能失败或输出质量不足。Finalize 阶段是系统最后的防线，确保输出报告不会出现关键区块为空的情况。

### 8.1 质量门检查

完成洞察和 Critic 之后，系统会对结果做一次体检：

- 情节线是否存在且有事件？如果为空，根据章节摘要自动回填主线事件（均匀抽取若干章节摘要作为锚点）。
- 差异化亮点是否过少？如果不足 3 条，根据情节线和节奏数据自动生成基础差异点（如"节奏策略：高强度爽点间隔短"）。
- 读者爽点公式是否过少？如果不足 5 条，统计钩子类型分布，把最高频的 hook 类型转化为爽点公式。
- 弃书风险是否为空？如果为空，把 pacing 模块检测出的弃书风险区间转化成 DropRisk 对象。

这些回填都是确定性的，不调用 LLM，不受 API 失败影响，保证报告一定有内容。

### 8.2 分线总结的兜底

"长篇智能体总结"是报告里展示每条情节线分阶段概述的模块。这个数据有两个来源：

- 优先用 LLM 生成的版本（在情节线复核时顺带产生）
- 如果 LLM 版本为空，用确定性算法生成：把每条线的事件按时间轴四等分（铺垫/触发/升级/回收），每段取前几个事件标题拼接成焦点描述，再均匀抽样若干里程碑事件。

这个兜底机制解决了之前"长篇智能体总结为空"的 bug——原因是 LLM 版本有时会因为 JSON 解析失败而为空，但模板侧没有处理这种情况，导致展示为空。

## 九、知识图谱：把分析结果转化为可导航的关系网络

报告里的关系图谱不只是为了好看，而是要把整本书的人物、章节、事件、套路、金句之间的关系以可视化方式呈现。

### 9.1 图谱结构

**节点类型**：

- Book：书本身，唯一根节点
- Chapter：每一章
- Character：追踪到的人物
- Location：出现的场景地点
- Event：情节线上的关键事件
- Trope：命中的题材套路
- Quote：精选金句

**关系类型**：

- CONTAINS_CHAPTER：Book → Chapter
- APPEARS_IN：Character → Chapter（这个人物在哪几章出现）
- EVOLVES_TO：Chapter → Chapter（人物的弧光状态转变，两个章节之间的演化关系）
- RELATIONSHIP_WITH：Character ↔ Character（人物之间的关系，含关系类型）
- SET_IN：Chapter → Location（这一章发生在哪里）
- BELONGS_TO_LINE：Chapter → Event（章节包含某条情节线的关键事件）
- PARTICIPATES_IN：Character → Event（人物参与了某个关键事件）
- USES_TROPE：Chapter → Trope
- CONTAINS_QUOTE：Chapter → Quote

### 9.2 双格式输出

图谱同时输出两种格式：

**Cypher 脚本**：如果用户有 Neo4j 环境（通过 Docker 启动），可以直接把这个 Cypher 文件导入，得到一个完整可查询的图数据库。支持用图查询语言写各种分析查询，比如"找出所有和孙悟空直接相连的事件节点"。

**JSON 文件（Cytoscape.js 格式）**：直接嵌入 HTML 报告里，在浏览器端用 Cytoscape.js 渲染成可交互的图谱。用户可以点击节点聚焦邻域、隐藏章节节点（减少视觉噪音）、重新布局。

### 9.3 大图降噪

对于长篇小说，章节多、人物多，图谱节点可能超过 1000 个，全量渲染会很卡。系统会在渲染前做降噪：

- Character 和 Event 节点优先保留
- Chapter 节点按度数（连接边数量）排序，只保留最重要的 120 个
- 非章节节点按重要性评分（类型基础分 + 连接度 × 权重）排序，保留前 300 个
- 最终边数不超过 1800 条

这样渲染出来的图谱仍然包含最重要的结构信息，但不会因为节点太多而无法使用。完整的图数据仍然保存在 graph.json 里，不会丢失。

## 十、输出层：从分析到可复用资产

### 10.1 交互式 HTML 报告

报告使用 Jinja2 模板渲染，不依赖外部服务，是一个完全自包含的单 HTML 文件。

报告包含 8 个标签页：

**概览**：关键指标卡片（追踪人物数、主线事件数、情节线总数等）、主线/暗线连续性体检表（每条线的覆盖范围和 span_ratio）、差异化亮点表格、读者爽点公式列表。

**爽点节奏**：两个图表——左边是用 ECharts 渲染的爽点强度曲线（X 轴章节序号，Y 轴强度，红色背景标注弃书风险区间，星标标注强度 5 的高峰）；右边是钩子类型分布饼图。下方是弃书风险详情表格，每条风险附修复建议。

**主线/暗线**：顶部是可缩放的多线时间轴（ECharts scatter 图，每种线用不同颜色，点击节点显示事件详情）。中部是"长篇智能体总结"，每条线展开后可以看到分阶段概述（铺垫/触发/升级/回收）和里程碑事件。底部是每条线的详细事件表格，**新增了"节点事件/发生了什么/造成什么变化"三列**，让每个节点的因果关系更清晰。

**人物档案**：每个追踪人物一张卡片，包含角色定位、动机、缺陷、弧光五状态点表格、关系列表。

**关系图谱**：Cytoscape.js 渲染的知识图谱，支持点击节点聚焦邻域、隐藏章节节点、重新布局。

**深度洞察**：差异化亮点、读者爽点归因（含心理机制说明）、弃书风险与修复建议（完整三列版）。

**金句 + 套路**：金句列表（含出处章节和为什么是金句）；套路命中频次表格（套路名称、实例描述、出现章节）。

**原始数据**：quality_gate 健康检查 JSON、完整 metrics.json、全部章节摘要表格。

### 10.2 创作宪法

创作宪法是一份给下游 LLM 用的指导文档，告诉 AI"写这种书要遵守哪些规则"。

它由专门的 deep agent 生成，输入是完整的全书分析上下文，输出是一份 Markdown 格式的"规则书"，内容包括：

- 题材定位：这本书的核心类型标签是什么
- 核心爽点公式：读者最爱的 3-5 种情节模式，每种附使用频率和触发条件
- 人物塑造要求：主角应该有什么特质，反派的作用是什么，CP 的推进节奏如何
- 节奏规范：每章爽点目标数量、章末钩子强度要求、高峰间隔目标
- 文风约束：POV、句长、对白比、核心标志性句式
- 必须避开的雷区：来自弃书风险分析的具体问题，如"连续多章无进展会触发弃书"

### 10.3 AI Writing Pack

写作包是整个项目最"产品化"的输出，目标是让用户可以把这几个文件直接拖进 Claude Project 或者 Cursor Rules，然后就能让 AI 写出风格相近的新书。

包含 6 个文件：

**system_prompt.md**：一份完整的 AI 创作系统提示，包含题材定位、文风约束、节奏目标、爽点公式、差异化要求、雷区清单、创作流程（先设计本章钩子再写正文等）。

**style_few_shot.md**：从原著提取的 3-5 段示范段落。在给 AI 写新章节之前先让它重读这几段，帮助它进入原著语感。

**characters.yaml**：所有主要角色的结构化档案（YAML 格式，便于 LLM 解析），包含角色 ID、名字、别名、角色定位、动机、缺陷、出场章节、弧光节点、关系列表。

**tropes.json**：分为三部分——must_use（原著已使用的套路，含实例和出现章节）、available（题材套路库里还没用到的可选套路）、anti_patterns（这个题材里的禁忌写法）。

**plot_skeleton.md**：主线/暗线的骨架 Markdown，按时间轴列出每条线的关键事件，以及与其他线的交汇点说明。

**creation_constitution.md**：创作宪法的副本，放进写作包方便一起导入。

## 十一、工程能力：让它能真正跑起来

### 11.1 多层断点续跑

长篇分析可能需要几十分钟。为了避免意外中断导致前功尽弃，系统在每个关键节点都做了持久化：

Map 阶段每章完成后立刻写入 SQLite，下次重启直接跳过已完成的章节。LLM 调用缓存也是 SQLite，相同 prompt 不重复调用，省钱且加速。向量库写入 Chroma 磁盘，复用时不重新 embedding。最终的全量分析结果写入 JSON，输出包也写入磁盘，每次都能增量更新。

### 11.2 成本控制

一次完整分析 100 章西游记（71 万字），`--tier basic` 档位（全 DeepSeek）成本约 0.03 美元，耗时约 7 分钟。

主要成本来自 Layer1 Map 的 100 次 DeepSeek 调用，每次约 3000 token in + 1000 token out，合计约 40 万 token，DeepSeek 收费约 0.056 美元 + 0.028 美元。

如果用 balanced 档位，Layer2/3 的 Claude 调用会额外增加约 0.5-2 美元，取决于书的复杂程度。

### 11.3 进度可观测性

系统在流水线的每个节点发出进度事件，CLI 层把这些事件翻译成 Rich 进度条和控制台输出，用户可以实时看到：

当前正在处理第几章（附章节号和当前总成本）、哪个智能体正在运行（arc/plotline/style/refine）、各智能体是否成功、Critic 校对了多少条结论、最终产物在哪里。

这对长任务非常重要——用户能知道是卡住了还是还在正常运行，以及大概还需要等多久。

### 11.4 失败隔离

每个阶段的失败都是隔离的：某一章 Map 失败，其他章节继续运行；某个 Reduce 子任务失败，报告仍然产出（只是对应模块数据为空或用兜底数据填充）；Critic 失败，洞察结果仍然保留（只是不做置信度校验）。

这种设计保证了在网络不稳定或 LLM API 偶发故障的情况下，系统仍然能产出一份完整的报告，而不是整体崩溃。

## 十二、技术亮点总结

### 亮点一：真正解决了上下文过长问题

不是靠"更大的上下文窗口"，而是靠"分层 Map-Reduce + 只在关键处用 RAG"这种架构设计，把百万字的信息压缩到每层可处理的粒度，同时保留了细节的可追溯性。

### 亮点二：主线/暗线有专门的工程保障

业界大多数方案直接用 LLM 猜情节线，对 3000 章的小说效果很差。本项目通过章节级 line_signals + Reduce 聚合 + RAG 复核 + 确定性修复的四层机制，把主线/暗线的贯穿性从一个"LLM 质量问题"变成了一个"可量化、可修复的工程问题"。

### 亮点三：所有结论强制携带原文证据

每个结论型字段都继承自 Evidenced 基类，必须携带 evidence_chapter（哪几章原文支持这个结论）。这个约束贯穿整个系统。配合 Critic 的原文回查校验，系统输出的结论比纯 LLM 猜测有更强的可信度。

### 亮点四：输出是可复用资产而非一次性报告

AI Writing Pack 的设计让这个系统的价值延伸到了分析之外。用户拿到分析结果后，可以直接把写作包导入 Claude 开始创作，而不是手动把报告内容重新整理成 LLM 提示词。这把"拆书"和"写书"两个流程连接了起来。

### 亮点五：LLM 失败不会导致报告崩溃

质量门 + 确定性兜底保证了报告的完整性。即使某些 LLM 调用失败，报告里对应的模块也会有合理的回填内容，而不是展示错误信息或空白区块。

## 十三、当前限制与后续方向

### 限制

**情节线仍有 JSON 解析风险**：Plotline refine 是当前最容易出现 JSON DecodeError 的地方，因为 LLM 输出的 JSON 偶尔格式不规范（缺引号、多逗号等）。这不影响主流程（有兜底），但会导致分线总结质量下降。

**long-form 中段注意力衰减**：即使做了分批处理，当一本书有 3000 章时，章节摘要本身聚合后仍然很长，LLM 的中段注意力问题依然存在。进一步的解决方向是更细粒度的卷级聚合。

**线路热力图缺失**：目前 line_signals 数据已经存在于 novel_analysis.json，但报告里还没有把"每章属于哪些线"做成热力图展示，这是一个可视化优化点。

### 后续方向

- 为情节线复核阶段增加 JSON 自动修复
- 把 line_signals 做成章节×线路的热力图
- 增加"伏笔-回收"自动配对检测
- 增加多书横向对比基线
- 把读者评论数据并入弃书风险和爽点归因的校准链路
- 给 AI Writing Pack 增加章节级创作模板（每章该如何开头、中段安排什么、怎么结尾）

## 十四、一句话核心

novel-lab 的本质是：**把"把整本书塞给 AI 总结"这个错误范式，替换为"像专业编辑一样对小说做分层结构化拆解"的正确范式**。每一个技术决策——章节切分、Map-Reduce、line_signals、RAG 复核、Critic 校验、确定性兜底——都是为了让 AI 输出的结论更接近专业编辑拆书时会得出的结论。
